# 性能优化第二轮 · 2026-10-20

保留赛博朋克卡通画面、头像面具、自由探索和电影演出，优化绘制、资源、碰撞、小游戏动画与空闲网络负载。未增加前端运行时依赖；Rust/WASM 是可复现的对照实验，不进入游戏构建。

## 实现

- 静态场景按空间网格、材质、阴影、图层与绘制顺序合批，保留剔除。宽视角用8米网格，窄竖屏用4米网格，控制屏外三角形的额外绘制。透明物体单独绘制，反射缩放、蒙皮和已有实例对象跳过。保持顶点、法线、UV与阴影标记；网格边缘仍可能多画少量三角形，这是减少绘制调用的取舍。
- 建筑和家具固定世界矩阵，人物头部只合批骨骼内部的固定部件，仍跟随头部运动。纸箱、公文包、电梯门、猫和扫地机器人独立动画。销毁合批时恢复源节点，不销毁共享材质。
- 人物球体、胶囊、面具和饰品共享不可变几何体，复用GPU缓冲。缓存参数是代码中的有限组常量，与人数和身份无关。外观相同的角色不因钱包或消息更新重复重建。
- 静态碰撞体建立空间索引，常用半径只对附近候选做原有精确检测；特殊半径保留全扫描。对照原算法覆盖10万个随机点、接触边界、网格接缝和非有限输入，原72条寻路检查继续通过。
- 小游戏卡片每帧用 `translate3d` 运动，ResizeObserver缓存尺寸，帧内不读布局；React时间显示改为10Hz。视觉命中区与输入判定仍使用实时服务端时间及同一阈值。完成/过期卡片释放高亮和合成提示；连续漏接即时更新状态引用，避免同帧护盾状态陈旧。
- 自动画质保留12秒预热、两窗降档/六窗恢复，并加入P95。持续中位帧时间超过20.5ms或P95超过34ms才降档；恢复需中位低于17.5ms且P95低于23ms。手动画质保持用户选择。
- 移动上报保持5Hz、起步/停步及时发送；静止心跳改为每5秒，闲置位置请求减少80%。隐藏页面只补停步包，失败会重试。SSE继续承担在线、交易与社交同步。失焦停止按键、摇杆和自动寻路。
- 修复界面切换后的灯光问题：R3F切换always/demand会重置场景Clock，旧阴影/灯光限流器缓存旧时间，导致更新冻结。两者改用单调时钟，并在性能探针提供更新计数供回归检查。

## 实测与范围

本机macOS/Chromium、生产构建、独立Go服务和临时数据库；桌面1280×720、手机尺寸390×844、DPR1、自动画质。预热后读取最近5秒，保留一个本轮渲染测试页。截图与原始数据见 [artifacts/performance-v2](../artifacts/performance-v2)，最终样本在 `browser-checks.json`。原有8787服务和存档保留。

| 最近5秒样本 | 桌面原版 → 本轮 | 手机尺寸原版 → 本轮 |
| --- | ---: | ---: |
| 平均绘制调用 | 630 → 484（-23.2%） | 438 → 374（-14.6%） |
| GPU登记几何体 | 1376 → 725（-47.3%） | 1376 → 718（-47.8%） |
| 平均绘制三角形 | 214196 → 228455 | 159859 → 162478 |
| CPU提交中位耗时 | 6.8 → 5.4ms | 4.7 → 4.2ms |
| 平均FPS | 58.1 → 59.9 | 60 → 60 |
| 帧间隔P95 | 18.7 → 19.6ms | 19.6 → 19.4ms |

资源数是探针记录的GPU驻留资源，与浏览过的视角有关。表中短窗口存在波动，桌面P95并未改善，不将其他指标下降换算成全场景帧率或长尾提升。竖屏采用4米网格后，此样本只增加约1.6%三角形；仍保留原画面内容。

基线在未打开弹窗时采集，确保旧版阴影正常更新。开关界面后至少等待5秒再比较，旧时钟故障期间偏低的绘制次数不用于衡量收益。`?perf=1` 的CPU指标是R3F帧回调和渲染提交时间，不等于GPU时间或所有异步React工作。

实际完整运行15秒小游戏：一局900帧动画、150次时钟驱动React更新（减少83.3%）；另一局接中1次，奖励8金币、成长10，页面显示「结算已核对」。键盘持续移动与摇杆按住/释放已检查，释放后归零。

打开/收起手机后，阴影更新计数1775→2498、附近灯光重选634→906，确认不再随渲染时钟重置而冻结。浏览器无运行时错误；依赖层的Three.Clock弃用提示仍在。

这是视口模拟，不代表实体手机GPU、触摸延迟、发热或续航测试。本机普通场景接近60Hz显示上限，绘制/资源的下降不能直接换算成同等FPS提升。仍需补中低端Android/iPhone及多人场景的帧时间长尾数据。

## WASM 对照

同一地图、同一10万个输入点，11次计时取中位，预先验证结果一致。本机Node v25.9.0 / darwin-arm64的记录：

| 实现 | 10万次查询中位耗时 |
| --- | ---: |
| 原JS全扫描 | 9.963ms |
| JS空间索引 | 3.201ms |
| Rust/WASM全扫描 | 10.980ms |

本组空间索引约快3.1倍。929字节、无依赖WASM内核已实际编译运行；相同全扫描算法加逐查询跨边界调用，在这里没有胜过JS。这只针对本内核和调用方式，整段寻路批处理或更重计算可另测。

优化后寻路微基准：首次1.628ms、中位0.264ms、P95为0.591ms，100个样本。这是Node CPU微基准，不是浏览器或真机FPS，不跨设备外推。

```sh
make perf             # 普通JS基准，不需要Rust
# 可选实验，一次性准备目标标准库
rustup target add wasm32-unknown-unknown
make perf-wasm        # 编译Rust内核，使用同一数据与JS对照
```

源码：[collision.rs](../experiments/performance/collision.rs)。原始结果：[cpu-benchmark.json](../artifacts/performance-v2/cpu-benchmark.json)。普通 `make up`、构建和测试均不需要Rust/WASM。

## 持续验证入口

- `?perf=1`：最近5秒的帧时间中位/P95、绘制、资源，以及阴影/灯光更新计数。
- `?perf=1&batching=0`：在同一构建关闭合批作局部A/B，其他优化仍保留。
- `npm run test:collision`、`npm run test:render`、`npm run test:arcade`：碰撞等价、合批边界、小游戏动画/判定回归，均纳入 `npm test`。

下一轮先补实体手机与10/30/50人场景数据；出现主线程长任务再对比Worker/WASM批处理，GPU瓶颈再测人物实例化与其他渲染后端。目前证据支持优先减少绘制与重复工作。
